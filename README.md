# OURS — A Little World for Two

两个人的私人数字空间：回忆相册、恋爱纪念日、共同愿望、每日心里话、私人餐厅、沉浸式做菜、采购清单、小游戏和加密情书。无需账号，数据默认只保存在当前设备。

线上版本：https://hongkuanyu.github.io/ours/

## 当前功能

- 日记式首页、真实记录生成的近期动态、那年今日和年度回顾
- 在一起天数、下一个纪念日、生日和下次见面倒计时
- 本地照片回忆相册：照片墙 / 时光胶片、年份筛选、查看、新增、编辑、删除、滑动切换
- 18 道默认菜谱、菜单分类筛选、自定义菜品和照片压缩
- 菜品想吃 / 她的最爱 / 计划日期、学习状态与采购清单

- 愿望完成日期、愿望与回忆双向关联
- 每日心里话、约会盲盒、情侣默契问答、自定义问题和翻牌小游戏
- 本地 AES-GCM 加密情书
- 小档案设置：昵称、在一起日期、生日、喜欢的颜色、下次见面、首页封面照片
- 智能菜谱识别预览：抖音 / 小红书分享文案、分享标题、复合食材、食材单位、编号步骤和短链接限制提示
- 带结构校验、照片校验和失败回滚的本地数据导入 / 导出
- 我们的日程：约会 CRUD、日历 / 列表、状态筛选、复制、预算、准备事项和 .ics 导出

- 全局搜索：回忆、菜谱、愿望、日程、心里话和做菜记录
- 共同待办、礼物、喜好、多图回忆与日记增强
- 可选双人云端空间：Supabase Auth、一次性邀请、RLS、私有照片、显式同步授权、离线队列和冲突选择；默认关闭

## 最重要的一条体验链

**她想吃 → 我学做 → 我做成功 → 我们一起吃 → 记录这一天 → 成为共同回忆**

1. 在私人餐厅标记想吃、她的最爱或计划日期。
2. 进入沉浸式做菜模式，逐步完成并保存进度。
3. 完成后记录评分、心得、她的反馈和成品照片。
4. 选择“把今天收进回忆”，系统预填日期、菜名、照片和来源菜谱。
5. 回忆保存后，可以从相册跳回原菜谱。

同一份做菜记录会检查 `cookingLogId`，不会自动生成重复回忆。真正创建回忆前仍由用户确认。

- 她的生日
- 我们喜欢的颜色

## 本地数据与备份

- 照片保存在 IndexedDB（数据库 `ours-local-media`）
- 菜谱、愿望、做菜记录、愿望纪念关联、小档案、采购清单、见面日期、每日记录和问答结果保存在 localStorage
- 导出备份会包含 localStorage 记录与 IndexedDB 照片
- 备份文件可能包含私人照片、信件线索和生活记录，只应保存在你信任的设备
- 导入前会校验版本、结构、字段类型、照片格式、数量和大小
- 导入时会先创建旧数据快照；写入失败会恢复原记录和原照片，避免半覆盖
- 数据不会自动同步到另一台设备，也不会自动上传到第三方服务
- 清除浏览器站点数据会删除本地记录，重要内容请定期导出备份

## 智能菜谱导入

在自定义菜品编辑器顶部可以粘贴：

- 抖音或小红书的分享文案
- 菜品短链接
- 详情页里包含“食材”和“做法”的整段文字

系统会先显示预览，再等待用户确认：

- 菜名、来源平台、食材数量、步骤数量和建议耗时
- 缺失信息和需要人工检查的字段
- 编号步骤、常见计量单位和无关分享文案会被尽量清理

受抖音、小红书跨域、登录和反爬限制，纯静态版本无法只凭短链接稳定读取正文。只粘贴短链接时，系统只保留来源并明确提示限制，不会伪造食材或步骤。系统不会把内容发送给第三方抓取服务。若编辑器里已有未保存内容，确认填入前会再次提示，避免静默覆盖。

## 安全边界与情书暗号

GitHub Pages 是公开静态托管。知道网址的人仍可访问公开页面源码与静态资源；`noindex`、`robots.txt`、隐藏链接都不是访问控制。

仓库示例暗号 `5201314` **只用于演示**，不能保护真实隐私。若要在公开仓库中放真实情书：

1. 在一个不提交到公开仓库的本地副本中打开 `make-secret.cjs`。
2. 临时替换 `passphrase` 和 `text`，使用只有你们知道且足够长的暗号。
3. 运行 `node make-secret.cjs`。
4. 只把生成的 `salt`、`iv`、`ciphertext` 替换进本地 `config.js`。
5. 不要在代码、README、提交记录或聊天截图中留下真实暗号。
6. 确认发布范围后再决定是否推送加密后的配置。

客户端加密不能替代账号授权、服务端权限和端到端加密。高风险内容不应仅依赖这个静态页面的情书暗号。

## 可选双人云端空间

当前线上默认仍是 Local Mode。`cloud-config.js` 的 URL 与 anon key 为空时，应用明确显示“未配置”，不会伪装同步，也不会预加载远程私人数据。

已实现的安全边界与流程：

- 两位成员分别使用邮箱与密码登录，通过一次性邀请码绑定唯一双人空间
- 活跃成员上限为 2 人；邀请码 24 小时过期且只能使用一次
- 数据表和私有 Storage Bucket 均启用 RLS，只允许该空间成员读取
- 前端只允许公开 anon key；service role key 不得进入浏览器代码
- 用户首次点击“确认并开启双向同步”后，才会读取云端数据或上传本机记录与照片
- 离线修改进入本地队列；版本冲突必须明确选择“保留本机”或“使用云端”
- Local Mode、本地备份和 IndexedDB 照片不依赖云端，可继续独立使用

启用真实云端前，请严格按 `docs/cloud-couple-mode.md` 执行 SQL、配置 Supabase，并用两个独立账号验收 RLS、照片权限、冲突和账号撤销。当前尚未运行真实 Supabase 后端，不应把 mock 测试视为线上安全验收。
